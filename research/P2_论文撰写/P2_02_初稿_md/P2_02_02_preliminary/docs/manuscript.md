# Preliminary: Terminology and Evidence States

This section fixes the vocabulary used by the rest of the manuscript. The goal is not to add another contribution claim, rehearse the full related-work argument, or report experiment results. The goal is to make the evidence-governed workflow auditable by defining the smallest set of terms a reviewer needs before reading the workflow figure, methods, and result tables. In this manuscript, an evidence-governed human-agent research workflow is a bounded sequence of node-local authoring, checking, review, response, and downgrade decisions. It is not treated as an autonomous scientific-discovery engine, and it does not turn generated files, scheduler projections, or successful command exits into scientific evidence by themselves.

A node is the smallest schedulable research unit. Each node owns its local manuscript fragment, prompt assets, review files, status record, and optional artifacts. A node-local artifact is a file that can be inspected by an author or reviewer and that records a specific decision, mapping, ledger, figure provenance, table plan, or evidence boundary. The manuscript uses stable identifiers to prevent these files from drifting apart. A `claim_id` names a manuscript assertion or planned assertion. An `evidence_id` names the artifact, ledger row, figure source, or verified citation record that can support or limit that assertion. A `protocol_id` names the rule or gate that decides whether evidence is eligible for a stronger claim. A `support_status` states the current strength of support. A `boundary_label` states what the evidence must not be used to claim.

The distinction between author exit and node close is central. Author exit means that a local authoring pass has created the required files and answered the node's key research judgment, or has explicitly recorded the gap. Node close is stricter: the node has passed the required independent review gate, the reviewer verdict is complete, hard failures are absent, reviewer independence is confirmed, and comments are responded to in the node-local response file. This distinction prevents a polished paragraph or a complete-looking artifact from being treated as a closed research unit before review and response coverage exist. It also gives negative or rejected evidence a durable place in the workflow rather than allowing it to disappear when a node progresses.

The evidence vocabulary is deliberately conservative. A verified citation context can support prior-work positioning, reporting-policy motivation, or terminology, but it does not support this workflow's final empirical performance. Protocol-supported evidence can justify a planned method, gate, or table structure, but it is not a result row. A supported-limited proxy can illustrate a bounded sanity check, such as a synthetic/offline signal, only under its boundary label. Blocked-pending-gate evidence is visible but cannot be upgraded until the named gate passes. Rejected evidence records a failed or non-selection-eligible row and remains part of the paper's evidence base. Unsupported and unclear states are not errors to hide; they are labels that prevent rhetorical overclaiming.

These definitions also set the related-work and methods boundaries. Prior work belongs in the positioning layer when it explains why tool-using agents, multi-agent frameworks, automated experimentation, or automated writing motivate the problem. It should not be used in this preliminary section to prove that the proposed workflow works. The methods section, by contrast, will specify the node-local contract, review gate, response closure, negative-result retention, and PHM-Vibench to PHMGA responsibility boundary. The preliminary section only names these concepts and states how their identifiers relate. It does not describe algorithms, provider calls, formal result rows, ablation design, or backend selection.

For the downstream workflow figure and tables, every accepted display item must therefore have a claim reference, an evidence reference, and a boundary. A workflow schematic can explain the path from claim to evidence to review to response, but it is not evidence of performance. A result table can report a formal row only when its parser-facing ledger, dataset alignment, backend eligibility, repeat policy, and artifact contract are satisfied. A negative or unclear row must remain visible because hiding it would make the claim-evidence chain look stronger than the workspace actually supports.

The practical reader check is therefore simple. For every later claim, figure, table row, or response item, the manuscript must be able to answer five questions: what is being claimed, what artifact or ledger row supports it, which protocol made that evidence eligible, what boundary prevents overuse, and which review or response record closed the objection? The node-local term contract in `artifacts/preliminary_term_contract.yaml` maps each preliminary term to that downstream check. If any element is missing, the correct manuscript action is to downgrade, block, or report the gap rather than write a stronger claim.
